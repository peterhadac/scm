# English/Slovak Site Translation Implementation Plan

**Goal:** Translate the whole site to Slovak as a second language with a
switcher, per `docs/superpowers/specs/2026-07-11-i18n-en-sk-design.md`.

**Tech:** Starlight's built-in i18n (`locales` config) — no new dependency,
`@astrojs/starlight@0.41.1` already installed and already ships a complete
Slovak translation of its own chrome.

---

### Task 1: Starlight i18n config, sidebar translations, persistence script

**Files:** Modify `astro.config.mjs`

- [x] Add `locales: { root: { label: 'English', lang: 'en' }, sk: { label: 'Slovensky', lang: 'sk' } }` to the `starlight({...})` call.
- [x] Add `translations: { sk: '...' }` to each sidebar group/item whose Slovak
      label differs from the English one (loanwords like "French Press",
      "V60", "Aeropress", "Filterccino" are left without a `translations` key
      since the Slovak label is identical — Starlight falls back to `label`).
      `link` values are left unprefixed; Starlight injects the active locale
      automatically (verified in the installed package's
      `utils/navigation.ts:linkFromSidebarLinkItem`).
- [x] Add a third `head` script entry (alongside the existing two Ko-fi
      widget scripts) implementing the persistence redirect + `change`
      listener described in the design doc.

Expected: `npm run build` succeeds and produces both `/scm/...` and
`/scm/sk/...` route trees.

### Task 2: EN/SK data layer (`src/lib/i18n.ts`)

**Files:** Create `src/lib/i18n.ts`

- [x] `Lang = 'en' | 'sk'` type.
- [x] `UI` string table for every piece of `CoffeeTable.astro` chrome text
      (search, filters, table headers, empty states, stale-price
      tooltip/aria-label, legend, summary line), including Slovak count-based
      pluralization for "N coffees"/"N roasters" (1 / 2–4 / 5+, or 0) via a
      shared `skCount()` helper.
- [x] `ORIGIN_LABELS` — proper-cased Slovak display names for every country
      key in `data/coffee_origins.yaml` plus the `"Blend"` sentinel
      (`data/coffee_origins.yaml`'s own Slovak entries are lowercase parsing
      *aliases*, not display-cased names, so they aren't reused directly).
- [x] `PROCESS_LABELS` / `ROAST_TYPE_LABELS` — the controlled vocab from
      `CLAUDE.md`'s Data Schema.
- [x] `localizedOrigin()` / `localizedProcess()` / `localizedRoastType()`
      helpers, each falling back to the raw English value if a key is
      somehow missing from its map (defense against future vocab additions
      the map hasn't caught up with yet).

No Node built-ins in this module — required so it can be imported both from
`CoffeeTable.astro`'s server-side frontmatter and its client `<script>`.

### Task 3: Localize `CoffeeTable.astro`

**Files:** Modify `src/components/CoffeeTable.astro`

- [x] Read `const lang = Astro.locals.starlightRoute.lang === 'sk' ? 'sk' : 'en'` server-side; `const t = UI[lang]`.
- [x] Replace every hardcoded UI string (search label/placeholder, filters
      toggle, roaster/origin/process/roast labels, "All", clear button,
      table headers, empty states, legend, best-value badge, stale-price
      title/aria-label, summary line) with `t.*` lookups.
- [x] Per-row `originLabel`/`processLabel` computed via the Task 2 helpers
      and rendered in place of the raw scraped value — `data-origin` /
      `data-process` / `data-roast` attributes keep the raw English value.
- [x] Client `<script>`: import `UI`/`ORIGIN_LABELS`/`PROCESS_LABELS` from
      `../lib/i18n` directly (Astro/Vite bundles this for the browser since
      it's a normal, non-`is:inline` script). Read
      `document.documentElement.lang` (set by Starlight) instead of a custom
      data attribute. `populateSelect()` now builds `{value, label}` pairs —
      `value` stays the raw English key used by `applyFilters()`'s equality
      checks, `label` is the localized text, sorted by `label.localeCompare(lang)`.
      `resultCount`/empty-state text and the sort collator locale also use
      `t`/`lang`.

Expected: no leftover hardcoded English strings in the rendered table
markup when `lang === 'sk'`.

## Self-Review

**Spec coverage:** all four design decisions (Starlight i18n over custom
toggle, whole-site scope, controlled-vocab-only data translation with
stable filter keys, persisted choice) map onto Tasks 1–4 above.

**Type consistency:** `Lang`, `UI`, `ORIGIN_LABELS`, `PROCESS_LABELS`,
`ROAST_TYPE_LABELS` are defined once in `src/lib/i18n.ts` and imported
identically by both `CoffeeTable.astro`'s frontmatter (server) and its
`<script>` (client) — no duplicated string tables to drift apart.

**Scope check:** roaster/product names, and content already effectively
identical between languages (established loanword drink/brew names), were
deliberately left untranslated per the design doc — not a gap, a decision.
